REAL SYSTEMS & FAILURES

从真实业务
理解为什么要组合多种存储

技术真正变得清晰的时刻，是你能解释“如果不用它会怎样”。这一页用消费金融、电商、日志分析、AI RAG 与故障场景把各类存储技术串起来。

01

消费金融：注册 → 授信 → 借款 → 还款

手机号注册Redis 保存 OTP、限流计数；MySQL 保存账户主数据。
额度申请Redis 幂等防重；MySQL 保存申请状态机。
资料上传身份证/合同放对象存储，DB 只存 object key 与元数据。
风控审批Kafka 发布事件，风控服务异步消费；结果回写核心 DB。
借款MySQL 强事务记录借据、账务、状态变更。
还款唯一流水号 + 幂等约束；避免重复扣款。
搜索/运营Elasticsearch 做检索，避免核心库承担全文搜索。
分析ClickHouse / Lake 做历史分析和模型训练。
架构关键：Redis 解决“快”，MySQL 解决“真”，Kafka 解决“解耦”，Object Storage 解决“大文件”，ES 解决“搜”，ClickHouse/Lake 解决“分析”。
02

电商：为什么一个订单系统会用六种存储

数据更合适的技术原因
订单主状态MySQL/Postgres事务、唯一约束、关系完整性
商品图片S3/Object Storage海量大对象、低成本、CDN 友好
热门商品详情Redis高 QPS、热点读取
商品搜索Elasticsearch分词、倒排索引、相关性排序
订单事件Kafka异步通知、库存、物流、数据平台解耦
BI 报表ClickHouse海量列式聚合
为什么不用 MySQL 一把梭？ 可以“做”，但成本会越来越高：图片 BLOB 撑大表；全文 LIKE 扫描慢；热门查询压垮核心库；异步任务耦合；复杂报表抢 OLTP 资源。
03

日志平台：ELK / Kafka / Object Storage 如何协作

App Logs→Kafka→Log Pipeline→Elasticsearch+S3

Elasticsearch 保存“可快速搜”的窗口

例如近 7~30 天日志。查询错误码、trace_id、关键字很快，但成本较高。

S3 保存“长期原始数据”

例如一年历史日志。便宜，后续可用 Athena/Spark/Trino/ClickHouse 等分析。

核心思想：热数据和冷数据分层。不是所有数据都值得放最贵、最快的存储。
04

AI / RAG：对象、文本、向量其实是三种不同数据

原始 PDF / 图片S3/Object Storage
文档元数据Postgres/MySQL
Chunk 文本关系库/文档库/对象文件
EmbeddingVector DB / pgvector
关键词索引Elasticsearch/OpenSearch
最终检索向量相似 + 关键词 + Filter + Rerank
为什么只用向量不够？ “iPhone 17 Pro 256GB 黑色”这种查询包含精确属性。语义向量适合“意思接近”，而型号、价格、时间、权限等通常还需要结构化过滤或关键词检索。
05

故障推演 1：write() 成功后突然断电

情况 A数据仍在 Page Cache → 可能丢。
情况 BDB Redo 已 fsync，但数据页没刷 → 重启后可 Redo。
情况 CSSD 控制器缓存无掉电保护 → 即使 OS 认为 flush 完，也需依赖硬件保证。
结论：“持久化”是一条链。应用、OS、文件系统、设备缓存、SSD 控制器、NAND 任一层语义不同，都可能影响最终 Durability。
06

故障推演 2：Redis 锁过期，但业务还没执行完

时间线：T0 服务 A 获取锁 30s → T25 发生长 GC → T30 锁过期 → 服务 B 获取新锁 → T35 A 恢复继续写 → A/B 同时执行关键业务。

为什么唯一 token 还不够

token 能防止 A 误删 B 的锁，但不能阻止 A 在锁已失效后继续执行业务副作用。

业务怎么兜底

幂等键、唯一约束、版本号/Fencing Token、数据库事务、状态机条件更新。

07

故障推演 3：Kafka 重复消费

场景：消费者已经给用户发了优惠券，但在提交 offset 前崩溃。重启后再次收到同一消息，如果没有幂等机制，用户会拿到两张券。

错误做法

相信消息“只会来一次”。

正确做法

用 event_id / business_id 建唯一约束或幂等表，让同一个业务事件重复到达也只生效一次。

08

故障推演 4：数据库主库挂了

1. 检测故障心跳/租约判断 Leader 不可用。
2. 选择新主从足够新的副本中选举。
3. 防双主旧主必须失去写资格；否则会 Split Brain。
4. 客户端重连路由/代理/DNS/服务发现切向新主。
5. 修复旧主重同步日志或全量数据，再作为副本加入。
09

技术选型：先问工作负载，不要先问产品

  1. 数据是结构化关系，还是大对象/文档/时间序列/向量？
  2. 读多还是写多？随机 I/O 还是顺序扫描？
  3. 单条延迟重要，还是总吞吐重要？
  4. 是否需要事务、唯一约束、强一致？
  5. 是否允许最终一致？可以丢多少数据（RPO）？可以停多久（RTO）？
  6. 数据规模一年后会到多少？单机是否够？
  7. 冷热数据是否可以分层？
  8. 查询模式稳定还是高度灵活？
