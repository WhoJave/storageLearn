NAND 的关键限制

通常按 Page 写、按 Block 擦除，无法像 DRAM 那样任意原地覆盖，因此需要 FTL、GC、Wear Leveling 与 TRIM。

TLC / QLC

SLC/MLC/TLC/QLC 每 Cell 存储位数依次增加。容量成本下降，但写性能、耐久性和管理复杂度也发生变化。

设备与协议：NAND ≠ SSD ≠ NVMe ≠ PCIe

这四个词属于完全不同层级。

SATA / AHCI

源于机械硬盘时代，协议和队列模型更适合传统磁盘。SATA SSD 常见顺序吞吐约 500MB/s 级。

不足：SSD 已经快到协议本身开始成为瓶颈。

NVMe / PCIe

为低延迟 Flash 设计，支持大量并行队列，让多核 CPU 与 SSD 内部并行 NAND 通道更充分协作。

不足：成本、发热、PCIe Lane 与控制器资源要求更高。

FTL

把操作系统看到的 LBA 映射到真实 NAND Page。

同时负责磨损均衡、垃圾回收、坏块管理。

为什么 SSD 会“掉速”

SLC Cache 耗尽、GC、写放大、温度降频、可用空闲块减少都可能引发持续写性能下降。

04

Block / File / Object：现代云存储三大模型

这是理解 EBS、NAS、S3、Ceph、Kubernetes Volume 的关键。

Block Storage

向上提供“像硬盘一样”的逻辑块设备。

适合：数据库、虚拟机、操作系统盘、K8s PV。

产品：EBS、SAN、Ceph RBD。

不足：只认识 Block，不认识目录和文件。

File Storage

向上直接暴露文件和目录语义，多客户端共享。

适合：企业共享盘、NAS、开发目录、媒体协作。

产品：NFS、SMB、EFS、TrueNAS。

不足：大规模元数据和横向扩展更复杂。

Object Storage

以 Bucket + Object Key 管理对象，通过 HTTP/API 访问。

适合：图片、视频、备份、日志、AI 数据集、数据湖。

产品：S3、R2、OSS、COS、MinIO。

不足：不擅长文件中间随机 4KB 修改和 POSIX 语义。

工程常见组合：MySQL 存元数据与业务关系，S3 存大文件；数据库里保存 object_key / URL，而不是把大视频直接塞进 BLOB。

解决目录、权限、空间分配、一致性、元数据与快照。

inode

Linux 文件名通常先映射到 inode，再由 inode 记录权限、大小、时间与数据 Block 位置。

Journal

先写日志描述元数据更新，再真正修改文件系统。断电后可以 Replay，避免目录与 inode 等处于半完成状态。

Copy-on-Write

修改时写新 Block，再切换元数据指针。方便 Snapshot、快速复制和崩溃一致性。

06

数据软件全家桶：每一类到底解决什么问题

数据库不是一种东西，缓存、搜索、消息、OLAP、数据湖和向量检索都属于不同问题空间。

关系型数据库 · SQL

产品：MySQL、PostgreSQL、Oracle、SQL Server、SQLite。

解决：结构化数据、关系、事务、约束、索引。

场景：订单、支付、账务、用户、ERP、CRM。

不足：超大规模横向扩展、全文搜索、自由 Schema 不是其最自然优势。

Key-Value

产品：Redis、DynamoDB、RocksDB、LevelDB、etcd。

解决：按 Key 快速读写。

场景：缓存、Session、计数器、排行榜、配置、分布式协调。

不足：复杂关系查询弱。

文档数据库

产品：MongoDB、CouchDB、Firestore。

解决：JSON/嵌套对象与灵活 Schema。

场景：内容系统、商品属性、用户 Profile、快速迭代。

不足：复杂 JOIN、强关系模型常不如 SQL 自然。

宽列数据库

产品：Cassandra、HBase、ScyllaDB、Bigtable。

解决：PB 级水平扩展、大吞吐分布式写入。

场景：IoT、日志、用户行为、广告。

不足：建模往往围绕查询设计，通用关系查询能力弱。

图数据库

产品：Neo4j、Neptune、JanusGraph。

解决：关系网络遍历。

场景：社交、知识图谱、推荐、反欺诈。

不足：通用 OLTP 与大规模简单聚合未必合适。

时序数据库

产品：InfluxDB、TimescaleDB、Prometheus、VictoriaMetrics。

解决：timestamp + value 的高频写入、窗口聚合与保留策略。

场景：监控、IoT、行情、工业指标。

不足：复杂关系与普通业务事务不是主战场。

搜索引擎

产品：Elasticsearch、OpenSearch、Solr。

解决：倒排索引、全文检索、相关性排序、日志搜索。

场景：商品搜索、站内搜索、Observability、安全日志。

不足：通常不作为核心账本 Source of Truth。

缓存

产品：Redis、Memcached。

解决：把热点数据搬到更快层级，减少数据库压力。

场景：热点查询、Session、限流、验证码、锁。

不足：一致性、穿透、击穿、雪崩、内存成本。

消息 / 日志系统

产品：Kafka、Pulsar、RabbitMQ、RocketMQ。

解决：系统解耦、异步处理、事件流。

场景：订单事件、CDC、日志管道、流处理。

不足：重复消费、乱序、积压、语义和运维复杂。

数据仓库 / OLAP

产品：ClickHouse、Snowflake、BigQuery、Redshift、Doris、StarRocks。

解决：亿级/百亿级历史数据聚合分析。

场景：BI、报表、用户行为、指标平台。

不足：高频单行事务更新不如 OLTP。

数据湖 / Lakehouse

底层：S3 / HDFS；格式：Parquet / ORC；表格式：Iceberg / Delta / Hudi。

解决：海量原始与结构化数据统一保存、分析和 AI 使用。

不足：治理、元数据、事务和小文件管理复杂。

向量数据库

产品：Milvus、Qdrant、Weaviate、Pinecone、pgvector。

解决：Embedding 相似度检索与 ANN。

场景：RAG、语义搜索、推荐、图片检索。

不足：近似结果、索引成本、Embedding 质量决定上限。

重要：大型系统不是“选一个数据库”，而是 Polyglot Persistence——不同数据使用最适合它的存储模型。

Backup

Time Machine、Veeam、Restic、Borg、Velero 等解决误删、勒索、磁盘损坏与灾难恢复。

RAID ≠ Backup。 RAID 解决设备故障，不解决误删同步扩散。

3-2-1 原则

Git 也是存储系统

Git 通过 blob / tree / commit / tag 保存内容寻址对象与版本历史，本质是一个版本化 Content-Addressable Storage。

fsync 的意义

fsync() 要求把相关脏数据推进持久化路径。代价是延迟，因此所有数据库都在“每次都刷”与“批量刷”之间做性能/耐久性权衡。

Page Cache

把文件页缓存在 DRAM，读命中时不访问 SSD。

Journal

解决文件系统元数据更新到一半崩溃的问题。

FTL / GC

解决 NAND 不能随意覆盖、坏块、磨损均衡与回收问题。

B+Tree 为什么适合磁盘

每个 Page 可保存大量 key，使树高度很低，从而把“比较次数”转化成更少的随机 Page I/O。

主键聚簇索引叶子保存完整行；二级索引通常保存主键，因此查询可能发生回表。

Buffer Pool

热点索引页与数据页尽量驻留内存。高命中率下，大量 SELECT 根本不碰 SSD。

MVCC

通过事务 ID、Read View 与 Undo 版本链，让普通一致性读看到适合自己的历史版本，从而减少读写互相阻塞。

Gap / Next-Key Lock

在需要锁定范围的事务中，不仅锁已有记录，也可锁索引区间，防止范围内插入导致幻读。

核心模式：内存修改 + 顺序日志 + 后台刷数据页。顺序 WAL 换取随机数据页写入的高成本。

穿透

查不存在的数据，每次都落到 DB。方案：空值缓存、Bloom Filter。

击穿

超级热点 key 失效，大量请求同时访问 DB。方案：互斥重建、逻辑过期。

大量 key 同时过期或缓存集群故障。方案：随机 TTL、多级缓存、限流、熔断。

分布式锁

SET lock:key token NX PX 30000

token 必须唯一；释放锁要原子执行“比较 token + DEL”，常用 Lua。

仍不能自动解决网络分区、长 GC、业务执行超过 TTL、主从切换等问题。

持久化 / 高可用

RDB：快照、恢复快，但可能丢最近数据。

Partition + Key

Topic 分区后可横向扩展；Kafka 保证的是 Partition 内有序，不是全局有序。相同 key 常路由到同一 Partition，用来维持同一业务实体事件顺序。

Offset + Consumer Group

Consumer 保存自己的消费进度而不是“删消息”。一个 Group 内，同一 Partition 同时只分配给一个 Consumer，因此 Partition 数量决定并行度上限。

At-most-once先提交 offset，再处理；可能丢。
At-least-once先处理，再提交；可能重复。
Exactly-once依赖幂等生产者、事务与 offset 协调；外部副作用仍需幂等。
Kafka 为什么快：Append-only 顺序写 + Batch + Compression + Page Cache + Zero Copy。
E

主线 E：Sharding / Replication / Raft / CAP

单机时代结束后，系统开始面对容量、故障与“谁说了算”。

Sharding

把不同 Key/范围的数据放到不同节点，解决容量和吞吐扩展。

代价：路由、迁移、跨分片查询与事务更复杂。

Replication

复制多个副本解决节点故障。同步复制更稳但更慢；异步复制更快但可能丢最近写入。

Consensus

当出现超时、节点故障和网络分区时，需要确定 Leader 与已提交日志。Raft 是典型协议。

LeaderLog 1 · Log 2 · Log 3
↓ AppendEntries
Follower A
Follower B
2 / 3 多数确认 → Commit

一致性哈希

普通 mod hash 在节点数量变化时会导致大量 Key 迁移。一致性哈希把节点和 Key 放到 Hash Ring，只迁移局部范围。

CAP

关键不是日常“三选二”，而是当网络分区已经发生时：系统更偏向保持一致性（可能拒绝部分请求），还是保持可用性（允许暂时不一致）。

10

故障推演：真正理解系统从“坏掉”开始

架构设计不是看正常路径，而是问每个环节坏掉会怎样。

场景 1：write() 后立刻断电

如果数据只在 Page Cache，可能丢失。需要明确 fsync / WAL / 硬件掉电保护的耐久性边界。

场景 2：MySQL 已修改内存页但还没刷数据文件

Redo 已持久化时，可在重启后重放恢复；这就是 WAL 的价值。

场景 3：Redis 热点 Key 同时失效

大量请求穿透到 DB，形成击穿；需要互斥重建、逻辑过期或多级缓存。

场景 4：Kafka 消费成功但 Offset 没提交

重启后会再次消费，业务必须支持幂等。

场景 5：Leader 返回成功后、Follower 还没复制就宕机

异步复制可能丢最近数据；这就是 RPO 与延迟之间的权衡。

场景 6：网络分区导致两个节点都以为自己是 Leader

形成 Split Brain。需要基于多数派与任期的共识协议避免双主同时提交。
