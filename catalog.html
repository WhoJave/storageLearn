现代存储技术
完整目录与关系图

这一页专门回答最开始的问题：到底有哪些存储介质、设备、协议、文件系统、数据库与数据平台？每一类为什么存在、解决什么问题、什么时候用、有什么不足。

01

先建立“层”的概念

不要把 SSD、NVMe、ext4、MySQL、S3 当成同一层的东西。

物理层

真正保存 0/1：SRAM、DRAM、NAND、磁盘、磁带、光学介质。

抽象层

把裸硬件变得可管理：FTL、Block Device、文件系统、对象接口。

数据语义层

把“字节”变成业务可理解的数据：数据库、缓存、搜索、消息、数据仓库。

理解顺序：先问“数据物理上放哪”，再问“操作系统怎么访问”，最后问“业务如何查询和保证一致性”。
02

物理介质：从 CPU Cache 到磁带

所有存储设计都在速度、容量、成本、耐久性之间做交换。

介质大致特性为什么需要典型场景局限
SRAM极快、极贵、易失CPU 速度远快于内存L1/L2/L3 Cache容量非常小
DRAM快、易失给程序提供工作区系统内存、Buffer Pool、Page Cache掉电丢失
NAND Flash快、非易失替代大量机械随机 I/OSSD、UFS、U盘擦写寿命、写放大
HDD慢、便宜、容量大低成本海量存储NAS、备份、冷数据随机访问慢
Tape极便宜、顺序访问长期归档灾备、合规归档访问极慢
类比：SRAM 像桌面上的便签，DRAM 像办公桌，SSD 像抽屉，HDD 像仓库，磁带像异地档案馆。
03

SSD 内部到底发生什么

SSD 并不是“一块会随机覆盖的电子硬盘”。

1. 主机写 LBA操作系统告诉 SSD：“写逻辑块 1000”。
2. FTL 查映射控制器把逻辑地址映射到真实 NAND Page。
3. Out-of-place WriteNAND 通常不能直接原地覆盖，控制器会写新 Page。
4. 标旧页无效旧物理页变成垃圾，等待后续回收。
5. Garbage Collection搬运仍有效数据，擦除整个 Block，再释放空间。

Wear Leveling

尽量让不同 NAND Block 的擦写次数更均匀，避免某些区域提前老化。

TRIM

文件删除后，操作系统通知 SSD 哪些 LBA 已经不再需要，帮助 FTL 更高效回收。

为什么 SSD 会掉速？ 当 SLC Cache 用尽、可用空块减少、GC 加重、温度升高时，持续写速度可能明显下降。
04

SATA、SAS、PCIe、NVMe：别再混淆

SATA

传统存储接口/协议体系，适合 HDD 时代。队列和命令模型相对简单。

SAS

企业存储常见，强调可靠性、双端口与企业级特性。

PCIe

高速总线，负责设备与 CPU/芯片组之间传输数据。

NVMe

专门为低延迟非易失存储设计的协议，支持大量并行队列。

NAND物理介质→SSD设备→NVMe协议→PCIe总线
05

Block / File / Object：三种根本不同的存储模型

Block

像一块远程硬盘，只给你 Block 编号。数据库、VM 最喜欢。

例：EBS、SAN、Ceph RBD。

缺点：需要自己放文件系统。

File

直接提供文件/目录/权限语义，多个客户端可以共享。

例：NFS、SMB、NAS、EFS。

缺点：元数据扩展与一致性更复杂。

Object

以 key 获取完整对象，天然适合海量非结构化数据。

例：S3、OSS、COS、R2、MinIO。

缺点：不适合像本地文件一样频繁随机修改。

真实设计：电商商品图片放 S3，对象 key 存 MySQL；商品详情用 MySQL，热门详情放 Redis，全文检索放 Elasticsearch。
06

文件系统：从“块”变成“文件”

inode

记录文件元数据与数据块位置。目录负责“文件名 → inode”。

Journal

先记录即将修改的元数据，再真正修改，崩溃后可以重放。

COW

修改时写新块，再更新指针。快照与快速克隆因此变得简单。

系统常见平台特点
APFSAppleCOW、Snapshot、Encryption
NTFSWindowsACL、Journal、广泛兼容
ext4Linux成熟稳定、通用
XFSLinux Server大文件、高吞吐
ZFSNAS/ServerChecksum、COW、Snapshot、Pool
BtrfsLinuxCOW、Snapshot、Checksum
07

数据库与数据软件全家桶

不是“哪个最好”，而是“哪个数据问题更适合哪个模型”。

关系型 SQL

MySQL / PostgreSQL / Oracle / SQL Server。适合强关系、事务、约束、账务、订单。

弱点：大规模横向拆分复杂；全文检索不是长项。

Key-Value

Redis / DynamoDB / RocksDB / LevelDB / etcd。按 key 极快访问。

弱点：复杂关系查询弱。

Document

MongoDB / CouchDB / Firestore。JSON 结构自然，Schema 灵活。

弱点：强关系、多表复杂事务不如 SQL 自然。

Wide Column

Cassandra / HBase / ScyllaDB / Bigtable。大规模水平扩展与写入吞吐。

弱点：查询模式通常需要提前设计。

Graph

Neo4j / Neptune。适合多跳关系：社交、推荐、反欺诈、知识图谱。

Time Series

InfluxDB / TimescaleDB / Prometheus / VictoriaMetrics。专为 timestamp 数据优化。

Search

Elasticsearch / OpenSearch / Solr。倒排索引、全文检索、相关性排序。

Cache

Redis / Memcached。让热点数据靠近 CPU，减少 DB 压力。

Message/Event

Kafka / Pulsar / RabbitMQ / RocketMQ。异步解耦、事件流、日志管道。

OLAP

ClickHouse / BigQuery / Snowflake / Redshift / Doris / StarRocks。列式扫描、历史聚合。

Data Lake / Lakehouse

S3/HDFS + Parquet/ORC + Iceberg/Delta/Hudi。保存海量原始数据并提供表能力。

Vector DB

Milvus / Qdrant / Weaviate / Pinecone / pgvector。Embedding 相似检索、RAG、推荐。

08

数据湖为什么不是“大号文件夹”

Parquet

列式文件格式。查询只读取需要的列，并利用编码与压缩降低 I/O。

Iceberg

在对象存储文件之上增加 Snapshot、Schema Evolution、Partition Evolution、事务式元数据。

Lakehouse

目标是把数据湖的低成本/开放格式与数据仓库的表管理/一致性结合。

例：10TB 日志存 S3。BI 查询只需要 user_id、event、time 三列，Parquet 可避免读整行全部字段；Iceberg 再让这些文件像“表”一样有版本与元数据。
09

云原生与分布式存储

Ceph

同一底层集群可向上提供 RBD(Block)、CephFS(File)、RGW(Object)。

HDFS

把超大文件拆为 Block 分散存储并复制，适合批处理时代的大数据。

Kubernetes

Pod → PVC → PV → CSI → EBS/Ceph/NFS。计算生命周期和存储生命周期解耦。

RAID ≠ Backup。 RAID 主要防磁盘损坏，无法防误删、勒索软件、逻辑错误同步扩散。备份需要独立故障域。
10

五个问题，理解任何存储技术

  1. 数据真正存在哪里：RAM、SSD、Object Storage，还是远程副本？
  2. 什么时候算写成功：进内存、写 WAL、fsync，还是多数副本确认？
  3. 机器挂了怎么恢复：Journal、Redo、Replica、Snapshot、Replay？
  4. 并发冲突怎么处理：Lock、MVCC、CAS、Partition、Single Leader？
  5. 单机撑不住后怎么扩展：Cache、Replication、Sharding、Partition、Consensus？
