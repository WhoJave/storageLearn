这一页不再停留在“是什么”，而是继续追问：为什么这样设计？一次请求到底经过哪些层？崩溃时如何恢复？并发时谁和谁冲突？为什么性能优化总伴随一致性代价？

A

主线 A：write() 到 NAND 的完整路径

理解“写成功”和“真正持久化”不是一回事。

1. 应用调用 write()用户态进入内核态，数据通常先进入操作系统的 Page Cache。
2. Page 变 Dirty内存里的文件页被修改，但此时 SSD 可能完全没有变化。
3. 文件系统分配 Blockext4/XFS 根据 inode、Extent 等元数据决定逻辑文件位置映射到哪些块。
4. Block I/O 下发内核调度 I/O，经 NVMe Driver 提交到控制器队列。
5. SSD FTL 转换逻辑 LBA 被映射到物理 NAND Page。
6. NAND Program最终电荷状态改变，数据真正进入非易失介质。
关键陷阱：write() 返回成功，通常只代表数据已被内核接收；如果机器立刻断电，尚未刷出的 Dirty Page 仍可能丢失。

fsync 到底做什么

fsync(fd) 要求内核推进该文件的脏数据和必要元数据到稳定存储路径。它提高耐久性，但会增加延迟。

所以：每条业务写都立即 fsync 很安全，但吞吐低；批量 fsync 吞吐高，但可能扩大故障损失窗口。

为什么数据库有 WAL

随机修改数据页很慢，所以数据库先顺序追加一小段日志，再把真正的数据页延后刷盘。

思路：“先记录我准备怎么改”比“马上把所有散落的数据页都改完”更高效。

举例：转账记录从余额 1000 改成 900。数据库不必立刻找到并覆盖磁盘中的整页，而是先顺序写一条 Redo：“页 X 的字段 Y 从 1000 改成 900”。崩溃后可以重放。
B

主线 B：MySQL / InnoDB 一次事务发生了什么

SQL→Parser→Optimizer→B+Tree→Buffer Pool→Redo / Undo

B+Tree 为什么不是红黑树

磁盘最怕随机 I/O。B+Tree 每个节点能放很多 key，一个节点对应一个 Page，树高很低。

例如根页有 1000 个分支，下一层每个又有 1000 个分支，三四层就能覆盖非常大的数据量。

聚簇索引与回表

InnoDB 主键索引叶子通常保存完整行；二级索引叶子保存二级键 + 主键。

因此 where email=? 先在 email 索引找到主键，再回主键 B+Tree 取整行，这就是“回表”。

Redo Log

物理/页级恢复日志，服务于崩溃恢复。

Undo Log

保存旧版本，用于回滚与 MVCC。

Binlog

Server 层逻辑变更日志，用于复制、CDC、PITR。

UPDATE 执行定位目标记录，必要时加锁。
修改 Buffer Pool先改内存中的页。
生成 Undo保存旧值，保证回滚与历史版本读取。
写 Redo保证内存页还没落盘也能恢复。
提交协调Redo 与 Binlog 需要保持一致，MySQL 使用两阶段提交式协调。

MVCC 通俗理解

不是所有读都去抢锁。读事务拿到一个“时间视角”，根据 Read View 和 Undo 版本链找到自己应该看到的版本。

所以写事务可以继续产生新版本，旧读事务仍能看到旧版本。

锁仍然重要

MVCC 主要缓解读写冲突，但写写冲突仍需要锁。范围锁场景还会涉及 Gap Lock / Next-Key Lock。

消费金融例子：用户额度从 10,000 调整为 8,000。审批事务修改额度时，查询报表的旧事务仍可通过 MVCC 看到旧版本，而另一个同时修改额度的事务需要等待/冲突处理。
C

主线 C：Redis 不只是“内存快”

为什么快

数据在内存；数据结构针对常见操作优化；核心命令路径避免复杂线程竞争；网络与协议开销低。

为什么不能全放 Redis

内存贵；持久化语义与关系查询有限；强一致核心账本需要更稳健的事务与约束。

真正难点

缓存一致性、热点、过期、故障切换、分布式锁边界。

结构典型用途例子
String缓存、验证码、计数器SMS OTP、Session Token
Hash对象字段用户 Profile
Set去重、集合关系黑名单、标签
Sorted Set有序排名排行榜、延时任务评分
Bitmap布尔状态压缩签到、在线状态
HyperLogLog近似基数统计UV
Stream流式消息轻量事件处理

缓存穿透

查不存在 key → Redis miss → 每次打 DB。

解法：缓存空值、Bloom Filter。

缓存击穿

单个超级热点 key 过期 → 大量请求同时回源。

解法：互斥重建、逻辑过期。

缓存雪崩

大量 key 同时过期/集群故障 → DB 瞬间过载。

解法：随机 TTL、多级缓存、限流熔断。

登录验证码：SET otp:138xxxx 927314 EX 300。Redis 很适合 5 分钟有效的验证码，但真正“手机号是否已注册、账户是否冻结”仍应以数据库为准。
分布式锁：SET lock:key uniqueToken NX PX 30000 只是起点。释放必须“比较 token + DEL”原子执行；业务若执行超过 TTL，锁也可能失效。核心金融状态还需要唯一约束、幂等键和状态机兜底。
D

主线 D：Kafka 为什么像“可重复播放的日志”

Partition

Topic 被拆成多个追加日志。每个 Partition 内消息按 offset 有序，多个 Partition 之间没有全局顺序。

Key

同一业务 key 通常映射到同一 Partition，因此可以维护“同一个订单/用户”的事件顺序。

例：订单 1001 的 Created → Paid → Shipped 都用 key=1001，可落到同一 Partition；订单 1002 可以同时在另一个 Partition 并行处理。

At-most-once

先提交 offset，再处理。崩溃可能导致消息丢失。

At-least-once

先处理，再提交 offset。崩溃可能重复，因此消费者必须幂等。

Exactly-once

Kafka 内部可借助幂等生产者与事务降低重复，但写外部 DB/调用支付接口仍需要业务幂等。

为什么 Kafka 吞吐高

Append-only 顺序写、Batch、Compression、Page Cache，以及尽量减少用户态/内核态数据拷贝。

Consumer Group

同一组内，一个 Partition 同时只会被一个 Consumer 消费，因此 Partition 数限制并发度。

主线 E：分布式系统三问

数据放哪？放几份？谁说了算？

Sharding

解决单机容量和吞吐上限。

问题：节点增加时如何迁移？跨分片查询怎么办？

Replication

解决节点损坏和可用性。

问题：同步复制慢，异步复制可能丢最近数据。

Consensus

解决多个节点对“哪份状态有效”达成一致。

问题：超时、网络分区和故障选主。

Raft：Follower正常跟随 Leader，持续接收心跳和日志。
超时长时间没收到心跳，Follower 进入 Candidate。
RequestVoteCandidate 请求其他节点投票。
多数票获得多数后成为新 Leader。
AppendEntries新 Leader 继续复制日志，达到多数后提交。
CAP 的正确理解：不是日常状态下简单“任选两个”。真正讨论的是发生网络分区 P 时，系统更偏向拒绝部分请求来维持一致性 C，还是继续提供服务但允许暂时不一致 A。
例：3 个节点中 A 与 B 能互通，C 被网络隔离。多数派 A+B 可以继续选出 Leader；C 即使还活着，也不能单独对外确认新的强一致写入。
